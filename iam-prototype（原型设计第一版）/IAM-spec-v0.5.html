01概述

1.1 建设背景

公司现有 10,000 名员工、10 个分公司、111 个部门、54 个岗位，纳管 18 个业务系统、359 个功能点。各系统长期各自维护账号与权限，存在账号分散、人员变动权限不同步、授权无统一记录、调整依赖人工四类问题。

与此同时，公司还有数十个软件项目由外部实施团队承接。这些团队不在人事名册内，却需要访问代码库、测试环境和脱敏数据，其权限边界与生命周期必须与项目绑定，不能沿用内部员工的组织模型。

1.2 建设目标

  • 一个账号：内部员工一个账号通行全部已接入系统；外部与外包人员按项目单独开户。
  • 一处授权：内部按"岗位 → 角色模板 → 功能点 × 操作"授权，外包按"项目 → 资源"授权。
  • 一条流程：申请与审批在 IAM 内闭环，审批通过自动生效。
  • 一本明白账：授权、变更、登录、项目成员进出全部可追溯。

1.3 范围边界

范围内容说明
范围内IAM 自身开发与交付账号、组织、认证、授权、审批、审计全部模块真实实现
范围内18 个系统的档案与 359 个功能点作为授权对象登记，不改造业务系统
范围内外包项目与项目资源管理项目的账号、角色、资源范围、有效期由 IAM 管理
范围外业务系统自身改造与真实对接接口按 OIDC / OAuth2 预留
范围外OA 系统建设OA 视为已存在，仅约定集成
范围外考勤、门禁等硬件身份场景考勤系统作为接入方使用统一认证

1.4 建设原则

  • 单一事实来源：人的信息以 HR 为准，权限配置以 IAM 为准；外部与外包人员不写入人事表。
  • 默认最小权限：内部员工入职只有岗位模板权限；外包只有项目资源范围。
  • 职责分离：配置权、授权权、审计权三权分立，不设超级管理员。
  • 规则可解释：审批人、生效权限、失效清单都必须能说明计算依据。

02主体与角色模型

2.1 三类主体 v0.5 新增

账号表用 UserSource 区分来源。三类主体走两条完全不同的授权路径，互不混用。

类型来源归属授权路径有效期
内部HR 主数据同步分公司 → 部门 → 岗位岗位 → 角色模板 → 功能点 × 操作；叠加分公司 / 部门差量随在职状态
外包项目负责人提交团队清单项目（无组织归属）项目 → 项目角色 → 项目资源 × 操作必填，与项目周期一致
外部合作单位 / 监理 / 设计院等合作项目或合同同外包：按项目资源授权必填
边界：外包与外部人员不写入人事表，不占用部门编制，不出现在组织树的人数统计中；他们的账号只在"项目"视图下可见。

2.2 角色模板 v0.5 修订

角色不再是每个岗位一个，而是权限清单中已有的 5 个模板。岗位只决定"落到哪个模板"，不再各自派生角色。

角色模板人数可访问功能点说明
普通员工9,59667 / 359（19%）11 个"员"级岗位，覆盖 81% 的人员
部门经理277297 / 359（83%）部长、主任、主管等管理岗
项目经理108161 / 359（45%）项目经理、项目副经理、项目总工
公司领导19359 / 359（100%）董事长、总经理、副总经理等
业务系统管理员待定359 / 359清单中每项为"全部"；须按系统单独指定，不与 IAM 系统管理员混同

2.3 岗位映射

  • 建立"岗位 → 角色模板"映射表，54 个岗位全覆盖；映射由安全管理员维护，HR 岗位新增时产生待处理提示。
  • 映射变更前须显示影响人数（如"技术员 → 普通员工，影响 908 人"）并要求确认。
  • 同一岗位名称在不同分公司可以映射到同一模板，但权限差异由差量表达，不通过拆分角色解决。
命名冲突提醒：权限清单中的"系统管理员"指业务系统管理员（对各功能点有全部权限），与 IAM 内部的系统管理员（只维护档案、不参与授权）不是同一概念。界面上一律写作"业务系统管理员"与"IAM 系统管理员"。

2.4 治理角色与维护层级 v0.5.1

配置权限按"谁管下一级"分层：总公司管理员维护分公司差量并指定业务系统管理员，分公司管理员维护本分公司的部门差量。

治理角色职责边界
总公司管理员维护分公司差量、指定各系统的业务系统管理员、审批最高敏感级例外；可视作平台的超级用户不能删除或修改审计日志；不能审批自己的申请；所有操作纳入重点审计
分公司管理员维护本分公司的部门差量、审批中敏感级例外与跨部门申请不能修改分公司差量（只读）、不能跨分公司
部门负责人审批本部门的一级申请、复核部门内权限摘要不能配置差量、不能授予例外
安全管理员维护角色模板、岗位映射、敏感级标记，执行授权不能查看审计日志
系统管理员维护系统档案、功能点目录、组织同步不参与任何授权
审计员全量检索与导出只读，无任何写入
项目负责人创建项目、提交外包团队清单、项目内增删成员不能超出项目资源范围；扩大资源需审批
关于"超级用户"：总公司管理员是权限最高的配置者，但不是凌驾于审计之上的角色。三权分立仍然成立——它不能清除记录，也不能给自己或他人直接授予业务权限而不留痕。

03授权模型

3.1 内部员工：四层叠加 v0.5 修订

最终权限 = 角色模板（岗位映射）
　　　　　+ 分公司差量（增 / 禁）
　　　　　+ 部门差量（增 / 禁）
　　　　　+ 个人例外授予

每一层的授权对象都是"功能点 × 操作"的组合，例如"报销单 · 审批 / 查看 + 审批"。差量允许只调整其中一个操作——比如只禁"导出"而保留"查看"。

差量的主体是岗位，不是角色。角色模板只是岗位的默认权限包；同一部门里"会计"和"出纳"可能都映射到"普通员工"，但需要的权限不同，若差量挂在角色上，调整一个会误伤另一个。

层级作用域优先级与说明
角色模板全公司 × 角色最低优先级，默认授予
分公司差量分公司 × 岗位覆盖模板；用于区域合规、区域经营差异
部门差量分公司 × 部门 × 岗位覆盖分公司差量；用于"同岗位、不同部门职责不同"
例外授予用户 × 功能点 × 操作最高优先级，可覆盖任意层级的禁用；突破禁用须标注并进审计清单

3.2 为什么要部门差量

同名岗位在不同部门的职责差别很大，用一套角色模板或分公司差量都表达不了。典型例子：

岗位所在部门实际需要的权限
会计分公司财务部总账凭证：查看 / 新增 / 编辑；财务报表：查看 / 导出
会计第一项目经理部成本归集：查看；项目成本报表：查看；不可编辑总账凭证

两者岗位名相同、角色模板相同，差异全部用"项目经理部 × 会计"这一条部门差量表达：禁用总账凭证的编辑与新增。若用例外授予处理，会变成逐人配置，无法维护。

配置量估算：作用域组合是"部门 × 岗位"，理论组合数很大，但只配差异项；实际差异通常集中在 10–20 个岗位、少量关键部门，约 60–100 条，可维护。
维护层级：分公司差量由总公司管理员维护，部门差量由分公司管理员维护，逐级下放、逐级留痕。

3.3 外包团队：项目域授权 v0.5 新增

最终权限 = 项目角色授权 ∩ 项目资源范围 ∩ 有效期（项目状态 = 进行中）
  • 项目角色：开发、测试、实施、运维、项目经理，由项目负责人维护，跨项目复用。
  • 项目资源：代码库、测试环境、生产配置、脱敏数据、接口密钥、项目文档，逐项标注敏感级。
  • 交集语义：项目角色给"能做什么"，资源范围给"能对什么做"，两者取交集；任何一项缺失即无权。
  • 外包账号不参与功能点权限判定，也不出现在组织树、部门人数与内部权限摘要中。
项目角色典型资源与操作
开发代码库：读 / 写；测试环境：读 / 写 / 部署；脱敏数据：读
测试代码库：读；测试环境：读 / 写；缺陷库：读 / 写
实施生产配置：读；业务数据：只读（脱敏）；部署包：读
运维测试 / 生产环境：读 / 部署；日志：读；密钥：不可见

示例：A 团队只能访问 A 项目的代码库、A 项目测试环境与 A 项目脱敏数据，无法看到 B 项目任何资源。

3.4 权限敏感度分级 v0.5.1

例外申请的审批层级由权限敏感度决定，而不是一律两级。功能点增加"敏感级"字段（L1–L3），取一张申请单中最高的一级作为审批依据。

敏感级适用范围例外审批链
L1 一般OA 日常、即时通讯、知识库、会议室等协作类部门负责人 → 通过
L2 重要工程、物资、巡检、合同查阅等业务类部门负责人 → 分公司管理员
L3 高敏财务总账、薪酬、成本、个人信息、项目密钥、系统管理后台部门负责人 → 分公司管理员 → 总公司管理员

外包不适用该分级：外包的资源扩大统一走"项目归属部门负责人 → 安全管理员"，因为其对象是代码与数据，而不是业务功能点。

4.4 会话

  • 绝对到期：登录当日 23:59:59，不受下班时间与加班影响；到期前 10 分钟提示。
  • 统一登出：任一入口登出，全部会话失效；管理员可强制踢出。
  • 空闲超时默认关闭，可配置为 30 分钟。
  • 外包账号在项目结项、成员移除、有效期届满时立即踢出，不等待自然到期。

4.5 凭证策略

  • 密码 ≥ 8 位，含大小写、数字、符号中的三类；90 天强制更换，不得与最近 3 次重复。
  • 连续失败 5 次锁定 15 分钟，锁定期提示剩余时间。
  • 本期不启用多因素认证（模拟实验环境）；生产化前须补充。
  • 外包账号可附加 IP 白名单或设备限制（待评估）。

5.3 审批人解析

  • 内部：员工所在部门 → 部门信息表中的"部门经理"；为空或离职时上溯上级部门，最多三级，再到分公司管理员、总部安全管理员。
  • 外包：项目表 → 项目负责人；项目负责人同时是申请人时，上溯项目归属部门负责人。
  • 共同规则：不得自审；相邻节点为同一人时合并；审批人在办期间停用则单节点重算并留痕。
  • 节点停留超过 48 小时提醒，抄送上级，不自动通过。

5.4 生效方式

  • 审批通过即生效，或自指定日期起生效（后者先进入"待生效"状态）。
  • 外包账号不受"预约生效"影响：账号随项目立项生效，随项目结项失效。
  • 例外授予不设有效期、不复审；转岗时全部失效。

06审计

  • 四类日志：登录、权限变更、审批、管理操作；只写不可删，任何角色都没有删除入口。
  • 保留期限：在线 ≥ 1 年，归档 ≥ 3 年；销号仅脱敏个人字段，日志主体保留至归档期满。
  • 固定报表：例外授予清单（含"突破禁用"列）、分公司 / 部门差量对比、项目成员与资源清单、外包账号到期表。
  • 异常提示：非工作时间敏感授权、单人批量开户、项目结项后仍登录、短期大量导出。
  • 审计员只读；安全管理员无权查看审计日志；三权分立不设例外。
