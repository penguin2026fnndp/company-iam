统一权限管理系统（IAM）

本版只覆盖 10 月 27 日—29 日第一次检查：用面向功能的方式实现 RBAC0 模型。角色继承、约束、审批、差量、项目域全部移出本次范围。

版本 v0.6阶段：第一次检查交付 范围：RBAC0更新日期：2026-10-17 实现方式：面向功能

01概述

1.1 建设背景

公司现有多个业务系统，各自维护账号与权限，存在账号分散、人员变动权限不同步、授权无统一记录、调整依赖人工四类问题。IAM 的目标是把“谁、对什么、能做什么”收口到一处。

第一次检查不追求一次性解决全部问题，而是先建立一个可运行、可检查、可扩展的 RBAC0 内核：账号登录后，系统根据其角色实时算出权限，菜单和接口都按同一份结果判定。

1.2 本次目标

  • 一个账号：账号只表示“是谁”，不直接持有权限。
  • 一个角色：角色是权限包，用户通过角色获得权限，支持一人多角色。
  • 一枚权限：权限最小单元是“功能点 × 操作”，例如“财务报表 · 导出”。
  • 一处判定：菜单、页面、接口都从同一份权限集合派生，不维护第二份清单。

1.3 范围边界

范围内容说明
范围内登录、登出、当前用户服务端会话；演示环境用 localStorage 模拟
范围内用户管理列表、搜索、新增、修改、启停、重置密码、删除
范围内角色管理列表、搜索、新增、修改、删除、角色权限矩阵
范围内用户角色分配一人多角色，覆盖式保存
范围内权限目录按系统、模块、功能点、操作查询
范围内我的权限与菜单实时计算，按系统分组展示来源角色
范围内业务权限演示页财务报表页，用于证明业务菜单同样由权限驱动
范围外角色继承、角色层级RBAC1，第二次检查再做
范围外互斥角色、基数约束、先决条件RBAC2，第三次检查再做
范围外审批、差量、例外、项目域、外包生命周期v0.5 已描述，本版不实现
范围外审计报表、异常行为分析后续版本

1.4 建设原则

  • 最小权限：新用户创建后没有角色、没有权限，必须显式分配。
  • 角色不挂人：权限只配到角色，用户只挂角色；禁止给用户单独勾权限。
  • 单一事实来源：权限集合只从“用户角色 → 角色权限”计算，不在账号表里冗余。
  • 默认拒绝：菜单、路由、接口三层都先判断，没有明确授权就拒绝。

02RBAC0 模型

2.1 六个要素

要素本系统对应说明
User 用户sys_user登录主体，只保存身份信息，不保存权限
Role 角色sys_role权限包，可启停；一个角色可被多个用户持有
Permission 权限sys_permission功能点 × 操作，一行一个权限码
UA 用户角色sys_user_role用户与角色的多对多关系
PA 角色权限sys_role_permission角色与权限的多对多关系
Session 会话sys_session登录后签发，接口据此识别当前用户
RBAC0 的边界：角色之间没有继承关系，权限之间没有约束关系。一个人可以有多个角色，最终权限是这些角色权限的并集。

2.2 与本系统的映射

登录：账号 + 密码 → 创建会话
判定：会话 → 用户 → 用户角色 → 角色权限 → 权限码集合
使用：菜单按权限码过滤；路由按权限码守卫；接口按权限码返回 401 / 403

2.3 权限计算

“我的权限”只做一次三表关联，不在用户表里存权限快照。

SELECT DISTINCT p.perm_code
FROM sys_user_role ur
JOIN sys_role r ON r.id = ur.role_id AND r.status = 1
JOIN sys_role_permission rp ON rp.role_id = r.id
JOIN sys_permission p ON p.id = rp.permission_id AND p.status = 1
WHERE ur.user_id = ?

单点判断只需在上面的结果上加 AND p.perm_code = ?，或先取集合再在内存中判断。两种方式结果一致。

2.4 本版明确不做

能力RBAC 级别处理
角色继承、角色层级RBAC1第二次检查实现；本版角色表不建父子字段
互斥角色、基数约束、先决条件RBAC2第三次检查实现；本版不做约束表
差量、例外、审批扩展不进入第一次范围，避免把简单模型做复杂

3.3 权限码规范

统一使用“资源:动作”，需要区分系统时用“系统:资源:动作”。动作只允许六种：

动作编码示例
查看VIEWUSER:VIEW、FIN:RPT:VIEW
新增ADDUSER:ADD
编辑EDITUSER:EDIT
删除DELETEUSER:DELETE
分配ASSIGNUSER:ASSIGN_ROLE
导出EXPORTFIN:RPT:EXPORT
不要这样写：admin、canEditUser、role_admin。权限码描述“对什么做什么”，不描述“谁”。

3.4 三层鉴权

层做法失败表现
菜单静态菜单配置带权限码，登录后按权限集合过滤菜单不显示
路由进入页面前检查权限码显示 403 页，不渲染业务内容
接口每个功能方法第一行检查权限码返回 401 或 403，不执行 SQL
硬约束：前端隐藏不能代替接口校验。评审时直接在浏览器控制台调接口，必须得到 403。

3.5 关键业务规则

  • 新增用户默认没有角色、没有权限。
  • 一人可持有多个角色，权限取并集，重复权限只算一次。
  • 角色停用后，其权限立即从所有持有者的计算结果中消失。
  • 分配角色、重置密码、停用用户后，该用户当前会话立即失效。
  • 删除角色前检查成员数，仍有成员时返回 400。
  • 不能停用或删除当前登录账号，避免把自己锁死。

04账号与认证

4.1 登录

账号为工号，密码使用 BCrypt 存储。登录成功后签发会话，返回用户、角色、权限码与菜单；前端不再单独请求一次权限。

4.2 会话

项目规则
有效期登录当日 23:59:59，绝对到期
传递方式真实后端：Authorization: Bearer <sessionId>；演示原型：localStorage
失效时机主动登出、到期、账号停用、密码重置、角色变更
服务端校验每次请求查 sys_session，同时校验用户状态
演示原型的边界：前端 localStorage 会话可以被篡改，只用于课堂演示。真实后端必须由服务端签发并校验，不能把 userId 放在前端当身份。

4.3 密码与锁定

  • 密码使用 BCrypt（cost ≥ 10）存储，禁止明文入库。
  • 演示账号初始密码统一为 123456，仅用于课堂演示；真实环境执行“至少 8 位、三类字符、90 天更换”。
  • 连续失败 5 次锁定 15 分钟，锁定期提示剩余分钟数。
  • 管理员重置密码后，该用户全部会话失效。

4.4 账号生命周期

动作触发结果
创建管理员新增无角色、无权限，必须分配角色后才能看到业务菜单
停用管理员操作不能登录，已有会话立即失效
启用管理员操作恢复登录，权限按当前角色重新计算
删除管理员操作物理删除；不能删除当前登录账号

5.3 索引与约束

  • uk_user_account(account)、uk_role_code(code)、uk_perm_code(perm_code) 保证唯一。
  • sys_user_role 主键 (user_id, role_id)，另建 idx_ur_role(role_id) 支持反查成员。
  • sys_role_permission 主键 (role_id, permission_id)，另建 idx_rp_perm(permission_id)。
  • sys_session 建 idx_session_user(user_id, expire_at)，登录校验走该索引。
  • 关联表外键级联删除；删除角色前仍由业务层检查成员数，避免误删授权关系。

  • 前缀 /api，JSON 传输。
  • 返回 { code, data, message }；code=0 表示成功。
  • 错误码：400 参数或业务规则、401 未登录、403 无权限、404 不存在、409 唯一键冲突、500 服务器错误。

6.4 鉴权流程

  1. 拦截器读取 Authorization，查 sys_session，校验未过期、用户启用；失败返回 401。
  2. 把 userId 放入请求上下文，业务方法不接受前端传入的 userId。
  3. 功能方法第一行调用 permissionService.hasPerm(userId, "USER:VIEW")；失败返回 403。
  4. 通过后再执行 SQL，避免无权限请求打到数据库。

07面向功能实现约束

本版不使用面向对象分析与设计。设计单位是“功能”，不是“对象”。Java 里的类只作为编译单元和参数载体，不承担领域建模职责。

7.1 包结构

com.example.iam
├── auth/ 登录、登出、当前用户
├── user/ 用户增删改查、分配角色
├── role/ 角色增删改查、分配权限
├── permission/ 权限目录、我的权限
├── common/ Result、PageResult、异常、拦截器
└── config/ Web 配置、数据源配置

7.2 一条功能链

XxxController → XxxService → XxxMapper → SQL
  • 一个功能一个 Controller 方法、一个 Service 方法、一组 SQL。
  • Service 直接写具体类，不做 Service 接口 + Impl 两层。
  • 入参出参用 DTO / VO 普通类，字段与页面、接口一一对应。
  • 事务边界放在 Service 方法上，一个功能一个事务。
  • 权限判断写成普通方法调用，不引入注解切面以外的复杂机制。

7.3 禁止事项

禁止原因
建 User、Role 等带行为的领域实体本版是事务脚本，不是领域模型
继承、多态、聚合根、领域服务第一次检查不考 OO，做了反而增加理解成本
策略模式、工厂模式、抽象基类功能简单，抽象会掩盖主链路
为 RBAC1 / RBAC2 预建角色层级、约束表第二次、第三次再演进，避免过度设计

7.4 为什么第一次这样做

第二次检查要求“分别用面向功能和面向对象的方式实现 RBAC1”。如果第一次就把 OO 架构搭满，第二次就没有两种实现方式可对比。第一次保留清晰的事务脚本，第二次再在同一需求上做 OO 版本，差异才讲得清楚。

  • 菜单只显示当前权限允许的项；直接输入 URL 进入受限页面显示 403。
  • 新增、编辑、删除、分配等按钮按权限码显示；没有权限时只读。
  • 停用用户、重置密码、删除用户、删除角色均需二次确认。
  • 保存角色或权限后刷新当前登录人的权限与菜单，避免页面状态滞后。
  • 表格空状态、表单校验错误、接口 401/403 都有明确提示。

8.3 视觉规范

沿用现有原型的深色侧栏、浅灰背景、白色面板、蓝色主操作；状态使用绿 / 橙 / 红三色标签。权限码统一等宽字体，避免和功能名称混淆。
