统一权限管理系统（IAM）

面向全公司 1 万+ 员工的集中式身份与权限管理平台：一个公司账号通行全部业务系统，以岗位驱动的 RBAC 模型集中管理 20+ 系统的功能级权限，申请审批嵌入 OA 流程，系统自身按三权分立治理。

版本 v0.3（骨架） 阶段：需求分析 状态：待补充 更新日期：2026-10-15

01概述

1.1 建设背景

公司现有员工 1 万余人，业务系统 20 余个，各系统长期各自维护账号与权限，存在四类问题：账号分散、密码规则不一，员工记忆负担重；人员入职、转岗、离职时权限无法及时同步，遗留"幽灵账号"；权限授予无统一记录，审计时说不清谁为什么有什么权限；权限调整依赖人工逐系统操作，效率低且易错。

本项目建设的统一权限管理系统（以下简称 IAM）作为公司唯一的身份与授权中心，统一承载账号、认证、授权、审计四项能力。

1.2 建设目标

  • 一个账号：员工凭一个公司账号登录全部已接入系统，登录一次、全站通行。
  • 一处授权：权限统一在 IAM 中按"岗位—角色—功能点"授予，各系统不再单独维护权限。
  • 一条流程：权限申请与审批走 OA（外部 OA 对接或使用内置审批），审批通过后由 IAM 自动生效。
  • 一本明白账：所有授权、变更、登录行为可查可追溯，满足审计与合规要求。

1.3 范围边界

范围内容说明
范围内IAM 系统本身的开发与交付账号、组织、认证、权限、审批、审计全部模块真实实现
范围内20+ 业务系统的档案登记登记系统、模块、功能点清单，作为授权对象与权限目录
范围内与 OA 的集成接口提供标准接口，支持申请单发起与审批结果回调
范围外业务系统自身改造与真实对接业务系统仅作登记，不实施代码改造、不做真实联调
范围外OA 系统本身的建设OA 视为已存在，仅约定集成协议
范围外考勤、门禁等硬件类身份场景IAM 不承载考勤业务；考勤系统可作为接入方使用统一认证，其打卡峰值不计入 IAM 认证容量模型

1.4 建设原则

  • 单一事实来源：人的信息以 HR 为准，权限的配置以 IAM 为准，二者不重复维护。
  • 默认最小权限：员工入职仅获得岗位基线权限，额外权限一律通过申请获得。
  • 职责分离：授权的、配置的、审计的三类角色互相制约，无人可一手遮天。
  • 可审计：任何权限变更必须留下"谁、何时、给谁、改了什么、依据什么"的完整记录。

02术语与角色

2.1 术语表

术语定义
员工账号员工在 IAM 中的唯一身份标识，全公司唯一，不可自行修改用户名。
人员类型内部员工 / 外包人员。内部员工由 HR 同步产生，外包人员由部门管理员录入，以标签区分。
组织维度分公司 → 部门 → 岗位，三级结构，来源为 HR 主数据。
业务系统被纳管的 20+ 应用系统，含系统、模块、功能点三级结构。
功能点权限的最小授权单元，如"报销单-审批""员工档案-查看"。
公司角色全公司统一角色，与岗位对应，如"会计""销售主管"，一个角色包含跨系统的功能点集合。
基线角色某岗位在全公司的默认权限全集。
差量某分公司在某岗位基线上增加或禁用的功能点，用于表达分公司间权限差异。
例外授予员工在岗位权限之外单独申请获得的权限，记录在用户维度。

2.2 系统使用者与权限角色

角色职责关键约束
普通员工登录系统、使用已获权限、提交权限申请只能看到自己的权限与申请记录
部门负责人审批本部门员工的权限申请仅限本部门范围
部门管理员录入与维护本部门外包人员账号须填写有效期；不得修改内部员工 HR 数据
分公司管理员配置本分公司岗位差量、审批涉敏感权限申请仅限本分公司；变更全量留痕；总部可冻结回滚
系统管理员维护系统档案、功能点目录、组织架构同步、系统参数不参与任何权限授予
安全管理员定义角色、绑定功能点、授予与回收权限、标记敏感系统不能查看或修改审计日志
审计员查询日志、导出审计报表、发现异常操作只读，无任何配置与授权权限
系统对接方外部系统通过标准接口调用认证与鉴权服务接口级鉴权，仅返回必要字段
关键设计系统管理员、安全管理员、审计员三者互不兼任，不设超级管理员。任何单一账号都无法同时完成"授予权限"和"清除记录"两件事。

03总体业务模型

3.1 权限模型总览

采用以岗位为核心驱动的 RBAC 模型，权限沿"人 → 角色 → 功能点"传递，组织维度作为作用域与差异来源。

员工→ 公司角色（≈岗位）→ 功能点集合→ 业务系统
分公司→ 岗位差量（增 / 禁）→ 叠加到基线
  • 一个员工可拥有多个角色（身兼数职），最终权限为各角色权限并集。
  • 角色内权限按业务系统分段维护，互不干扰。
  • 分公司差异以"基线 + 差量"表达，避免为每个分公司复制整套角色。

3.2 典型业务闭环

场景触发系统处理结果
新员工入职HR 登记员工信息同步生成账号 → 按部门与岗位自动授予基线角色 → 叠加分公司差量员工可直接登录并使用岗位权限
员工转岗HR 变更部门 / 岗位回收旧基线角色 → 授予新基线角色 → 踢出已有会话权限即时与新岗位一致
员工离职HR 办理离职账号停用 → 会话失效 → 权限全部回收无法再登录任何系统
外包人员进场部门管理员录入生成带"外部人员"标签的账号，必填有效期有效期内可登录，到期自动停用
申请额外权限员工在 OA 提交申请按敏感度分级审批 → 通过后写入例外授予 → 事件留痕获得权限，永久有效（不设有效期）

04功能需求

4.1 账号管理

4.1.1 账号来源与主数据

编号需求描述优先级
FR-1.1系统应提供与 HR 系统的主数据同步接口，获取内部员工的姓名、所属分公司、所属部门、岗位、电话号码等信息。高
FR-1.2同步应为增量方式，支持定时与实时触发；HR 新增员工自动开户，信息变更自动同步，离职自动停用账号。高
FR-1.3同步任务应为异步执行，不得与认证服务争抢资源，且具备失败重试与异常告警能力。高
FR-1.4系统应支持外包人员账号的手工录入，由部门管理员操作，录入时须填写有效期，并自动打上"外部人员"标签。高
FR-1.5外包账号到达有效期后应自动停用，不依赖人工操作；管理员可续期。高
FR-1.6外包账号录入不设置审批环节（业务方确认）。中
FR-1.7外包人员账号字段与内部员工保持一致（姓名、所属分公司、所属部门、岗位、电话、用户名），另增"所属外包公司"（必填）与"合同 / 项目名称"（选填）两个字段，用于追责与按公司批量回收账号。高

4.1.2 账号规则

  • 用户名规则：姓名拼音；如发生重名，追加电话号码后四位。
  • 用户名一经生成不可修改，员工无自助改名入口。
  • 账号基础信息包含：姓名、所属分公司、所属部门、岗位、电话号码、用户名。
  • 账号状态：正常 / 停用 / 锁定。所有状态变更须记录操作人与原因。
  • 系统不采集身份证号等实名信息，以降低个人信息合规负担。

4.1.3 账号生命周期

阶段动作权限处理
入职HR 登记后自动开户自动授予部门 / 岗位基线角色
在职变更部门或岗位变动角色随之重算，旧角色回收
外包到期有效期届满账号自动停用，权限失效
离职HR 离职事件账号停用 + 会话踢出 + 权限回收
冻结管理员手工操作账号暂停，权限保留但不可用
到期预警外包账号到期前 15 / 7 / 1 天向部门管理员推送提醒（站内信 + 邮件）
销号停用满 2 年账号归档销号，保留脱敏的历史记录供审计追溯

4.2 组织与岗位管理

  • 组织架构为三级：分公司 → 部门 → 岗位，来源为 HR 主数据，IAM 内以只读方式展示。
  • 岗位目录由 HR 提供并同步至 IAM，作为公司角色绑定的依据。
  • 支持按分公司、部门、岗位维度检索人员与权限分布。
  • 组织架构调整（部门合并、岗位撤销）时，需提供影响面提示：受影响人数、受影响的角色与权限。
  • 职责分工：岗位目录由 HR 维护（人事概念），公司角色由安全管理员维护（权限概念），两者以 1:1 映射关联。
  • HR 侧岗位发生变动时，IAM 仅产生"待处理提示"，不自动创建或删除角色，由安全管理员确认后处理。

4.3 系统档案管理

编号需求描述优先级
FR-3.1系统应支持业务系统档案的录入与维护，字段包括：系统名称、系统编码、系统说明、负责人、状态。高
FR-3.2每个系统下可维护模块清单，每个模块下可维护功能点清单，含功能名称、功能说明、编码。高
FR-3.3功能点应预留类型字段（菜单 / 页面 / 按钮 / 接口等），本期统一为功能点粒度，为后续细化保留扩展能力。中
FR-3.4系统可被标记为"敏感系统"，由总部安全管理员维护，标记结果影响申请审批链的层级。高
FR-3.5支持后续新增系统：登记档案 → 维护功能点 → 纳入角色配置，无需改动系统架构。高
FR-3.6系统应提供标准接入接口（基于 OIDC / OAuth2），供后续业务系统真实对接认证与鉴权。中
说明本期纳管的 20+ 系统仅作为权限对象登记，不进行真实接口对接；对接接口按标准协议设计并预留，供后续启用。

4.4 认证与单点登录

4.4.1 统一认证

  • 全公司统一使用一个账号密码登录所有已接入系统，各业务系统本地账号不再作为登录入口（保留一个应急本地管理员账号）。
  • 支持统一登录门户与各系统间的免登录跳转（单点登录）。
  • 统一登出：用户在任一入口登出后，所有已建立的会话失效。
  • 会话有效期：当日有效，下班后自动失效；支持管理员强制踢出指定用户会话。

4.4.2 凭证与安全策略

策略项规则
密码复杂度不少于 8 位，需包含大小写字母、数字、符号中的至少三类
密码有效期90 天强制修改，不得与最近 3 次重复
失败锁定连续失败 5 次锁定账号 15 分钟
密码存储采用 bcrypt / Argon2 等不可逆算法加盐存储
传输安全全站 HTTPS / TLS
多因素认证一期实现：外网来源强制（账号密码 + 手机动态口令），内网来源免；按请求来源 IP 判定，支持后续扩展到全员强制

4.4.3 与 OA 的集成

  • 提供标准 REST 接口：OA 侧可发起权限申请单、传入审批结果、查询申请状态。
  • 同时提供内置轻量审批流，支持在无外部 OA 对接时独立运行。
  • OA 会话与 IAM 会话的衔接规则需明确：OA 登出时同步注销 IAM 会话。

4.4.4 内外网访问与多因素认证

  • 系统同时提供内网与公网两个访问入口，两者共用同一套账号体系与权限数据，不设"外网专用账号"，避免形成审计盲区。
  • 按请求来源 IP 判定访问来源（以网关侧记录的连接来源为准，不使用请求头中自报的地址，防止伪造绕过）：
    • 内网来源：账号密码校验通过后直接放行。
    • 外网来源：在账号密码校验之后追加第二因素（手机动态口令），未通过不得登录。
  • 外网侧仅部署接入层组件（反向代理、WAF、限流与防爆破）；认证服务、数据库、审计日志全部位于内网，个人数据不得存储于外网区域。
  • 针对外包账号，外网登录可在 MFA 基础上追加 IP 白名单或设备绑定限制（待评估）。
  • MFA 的绑定与解绑需提供管理流程：员工换号、更换设备时可由管理员重置，操作留痕。
  • VPN 若被认定为内网来源，则 VPN 自身的认证强度必须满足要求，否则"内网免 MFA"的策略形同虚设。

4.4.5 密码找回与重置

  • 员工可通过自助方式重置密码：校验手机号（与 HR 主数据一致）+ 工号后自行设置新密码，重置成功后强制踢出已有会话。
  • 自助失败（如手机号已变更）时走管理员兜底重置通道，须提交工单并由管理员操作，全程留痕。
  • 管理员重置属高风险操作，纳入审计重点监控范围。

4.5 角色与权限管理

4.5.1 角色定义

编号需求描述优先级
FR-5.1角色为全公司统一角色，与岗位对应，一个角色可包含多个系统的功能点。高
FR-5.2角色配置界面按业务系统分段展示，各系统的功能点独立配置，一处修改不影响其他系统。高
FR-5.3一个用户可同时拥有多个角色，最终权限为所有角色权限的并集。高
FR-5.4应提供角色的复制、停用、变更历史查询能力；角色停用后，已绑定的用户不再获得该角色权限。中

4.5.2 基线 + 差量（分公司差异）

  • 每个岗位对应一个全公司基线角色，定义该岗位的默认权限全集。
  • 分公司可对基线做差量调整，差量只记录"增加"与"禁用"的功能点，不复制完整角色。
  • 差量由各分公司管理员自行配置，约束为：仅可操作本分公司、变更全量记录日志、总部安全管理员可冻结或回滚任一分公司的差量。
  • 差量的最小作用域为分公司 × 岗位：一条差量对该分公司内所有使用该岗位的人员生效，不区分部门。
  • 同一分公司内、不同部门但同岗位的个别权限差异，通过例外授予解决，不将差量下沉到部门级。
  • 支持查看某分公司某岗位的"最终生效权限 = 基线 + 增量 − 禁用"的对照视图。

4.5.3 例外授予

  • 员工在岗位权限之外获得的额外权限，以用户维度的"例外授予"记录存储。
  • 例外授予不设有效期、不做定期复审（业务方确认），但必须完整记录申请人、审批人、授权时间与事由。
  • 提供例外授予清单查询，便于审计部门按需盘点。

4.5.4 权限可见范围

  • 默认最小可见：普通员工仅可查询本人权限与本人申请记录。
  • 部门负责人可查询本部门人员的权限摘要（不展开敏感系统的权限明细）。
  • 跨部门查询与全量权限清单导出，仅限安全管理员与审计员。

4.6 授权申请与审批

4.6.1 申请类型

  • 常规角色申请：申请本部门常用角色。
  • 跨部门 / 敏感系统权限申请：涉及被标记为敏感的系统，或超出本部门范围的角色。
  • 例外权限申请：在岗位权限之外单独申请若干功能点。
  • 外包人员账号申请：由部门管理员直接录入，不走审批。

4.6.2 审批链

申请类型审批链备注
常规角色（非敏感系统）部门负责人 → 通过一级审批
敏感系统 / 跨部门角色部门负责人 → 系统或分公司管理员 → 通过两级审批，敏感标记由总部维护
例外权限（永久）部门负责人 → 分公司管理员 → 通过记录为永久授权，不设到期
权限回收无需审批由 HR 事件或管理员直接触发

4.6.3 流程要求

提交申请→ 按敏感度定审批链→ 逐级审批→ IAM 自动生效→ 通知申请人
  • 申请单需包含：申请人、申请系统与功能点、事由、期望生效时间。
  • 审批通过后由系统自动授予权限，无需人工在业务系统中操作。
  • 支持撤回、驳回、转办；驳回须填写原因。
  • 全流程关键节点通知申请人，通知渠道为站内信（必达）+ 邮件（提醒）双通道，不采用短信。

4.7 审计与日志

日志类型记录内容
登录日志账号、时间、来源 IP、终端信息、成功 / 失败、失败原因
权限变更日志操作人、时间、对象用户、变更前权限、变更后权限、变更事由、关联申请单
审批日志申请单号、各审批节点、审批人、审批意见、时间
管理操作日志账号增删改、角色与功能点变更、系统档案变更、参数变更
  • 日志只写不可删：任何角色（含系统管理员）均无删除权限，写入后不可篡改。
  • 保留期限：在线 ≥ 1 年，归档 ≥ 3 年。
  • 审计员可按人、时间、系统、操作类型多维度检索并导出审计报表。
  • 支持异常行为提示：如短时间内大量授权、非工作时间敏感权限变更等。

4.8 自身权限管理

  • IAM 自身的功能点同样纳入统一权限树管理，遵循同一套 RBAC 规则。
  • 自身权限按三权分立配置：系统管理员（配置权）、安全管理员（授权权）、审计员（审计权），三者互斥，不可由同一账号兼任。
  • 管理员账号的登录与操作受更严格审计：登录需记录、关键操作需填写事由。
  • 管理员账号自身不得授予业务系统权限（除其本职岗位权限外）。

05权限判定规则

5.1 判定时机

采用实时判定模式：用户访问业务系统时，由 IAM 实时计算并返回该用户的权限清单，结果可做短时缓存（建议 5 分钟）。不使用"批量下发到各系统"的模式，以保证授权与回收的即时性。

5.2 生效权限计算公式

计算公式 最终权限 = （ Σ 用户岗位对应的基线角色权限 ∪ 用户其他角色权限 ）
　　　　　+ 分公司差量中的增量功能点
　　　　　− 分公司差量中的禁用功能点
　　　　　+ 该用户的例外授予功能点
  • 多角色取并集，不做交集，不设角色继承层级。
  • 差量中的"禁用"优先级高于基线，用于表达某分公司不可用的功能。
  • 例外授予为最高优先级追加，不可被差量禁用覆盖（如业务需要覆盖，需明确规则）。

5.3 回收机制

  • 权限判定即时生效：角色、差量、例外的任何变更，下一次判定即生效。
  • 已登录会话通过"会话踢出"机制强制失效，覆盖转岗、离职、权限回收场景。
  • 账号停用（离职、外包到期、管理员冻结）时，权限判定直接返回空。

7.1 数据安全细则

  • 手机号等个人敏感信息在界面上一律脱敏展示（如 138****8888），完整信息仅审计场景按权限查看。
  • 批量导出人员信息需单独审批，导出行为全程留痕（记录导出人、条件、条数、时间）。
  • 密码不可逆加密存储，接口返回体不得包含密码字段。
  • 管理员账号建议启用更严格的登录策略（如限制 IP 段、强制二次校验）。

08风险与已知取舍

以下为需求评审中已明确识别、并经业务方确认接受的风险，记录在案以便后续管控。

风险 R1 · 外包账号缺少职责分离外包人员账号由部门管理员手工录入，且不设审批环节；同时该管理员与本部门负责人角色常为同一人。存在"批量造号"风险，且无法通过流程制约。

管控建议：外包账号本身不授予敏感系统权限；对外包账号的开户行为做单独审计报表，由审计员定期抽查；管理员账号登录强制留痕。

风险 R2 · 例外授予纯永久导致权限沉淀例外权限不设有效期、不做定期复审，长期运行后会出现大量历史遗留权限，事由难以追溯，审计成本高。

管控建议：例外授予强制填写事由并关联申请单；提供按"授予时间超过 N 年 / 长期未使用"筛选的清单，供审计员主动盘点。

风险 R3 · 分公司差量自配可能失控差量由各分公司管理员自行配置，缺少统一节奏，可能出现同类岗位跨分公司权限差异难以解释。

管控建议：总部保留冻结与回滚权；提供"跨分公司同岗位权限差异对比"报表，供总部定期检视。

已确认取舍不做功能点到菜单 / 按钮级的细化、不实施业务系统真实对接、审批链不引入金额或数据量维度、内网不做设备绑定、一期不做"内网记住我"（免输密码）。以上均为主动取舍，后续按需扩展。

09待确认清单

本节记录需求评审中的待确认事项及其决议状态。已决议条目保留在案，便于追溯当时的取舍理由；未决条目继续挂起。

  • Q1 · 岗位目录的完整性与归属 已决议结论：岗位目录由 HR 维护（人事概念），公司角色由安全管理员维护（权限概念），两者以 1:1 映射关联；HR 侧岗位变动时系统仅产生待处理提示，不自动创建或删除角色。
  • Q2 · 外包人员录入的字段完整度 已决议结论：外包人员字段与内部员工一致（姓名、分公司、部门、电话、用户名），另增"所属外包公司"（必填，用于追责与按公司批量回收）与"合同 / 项目名称"（选填）；不采集身份证号等实名信息。
  • Q3 · 差量的粒度边界 已决议结论：差量最小作用域定为「分公司 × 岗位」；同一分公司内不同部门、同岗位的个别差异走例外授予，不下沉到部门级。理由：配置量可控，个别需求用个别机制处理。
  • Q4 · 通知渠道 已决议结论：站内信（必达）+ 邮件（提醒）双通道，不采用短信；外包账号到期前 15 / 7 / 1 天三次预警推送至部门管理员。
  • Q5 · 密码找回方式 已决议结论：一期实现自助重置（手机号 + 工号校验）；管理员重置作为兜底通道，须提工单并全程留痕。
  • Q6 · 登录终端的范围 已决议结论：内外网双入口，共用同一套账号与权限；内网来源账号密码直接放行，外网来源强制第二因素（MFA）；不区分账号类型，按请求来源 IP 判定策略；一期不做设备绑定。待确认：VPN 的发放与认证方式（若 VPN 门槛过低，内网免 MFA 的策略等于被绕过）。
  • Q7 · 考勤打卡是否纳入 已决议结论：不纳入 IAM 承载范围；考勤系统作为接入方使用统一认证，其打卡峰值由考勤系统自身承担，不计入 IAM 认证容量模型。
  • Q8 · 权限查询的开放范围 已决议结论：默认最小可见——员工仅可查询本人权限；部门负责人可查询本部门人员权限摘要；跨部门与全量查询仅限安全管理员与审计员。
  • Q9 · 数据保留与销号 已决议结论：离职即时停用账号；数据保留 2 年后销号，销号时保留脱敏的历史记录（用户名、权限变更记录）供审计追溯，与日志归档 3 年对齐。
  • Q10 · 部署与运维要求 部分决议已定：私有化部署，内网 + 外网双区，外网侧仅做接入层（反向代理 / WAF / 限流），认证服务、数据库、日志全部在内网，个人数据不落外网。仍待确认：① 是否有等保或行业合规要求（对外提供服务通常等级上抬，须先问清再定架构）；② 运维责任划分（建议硬件与中间件归 IT 运维、应用归开发方）。
