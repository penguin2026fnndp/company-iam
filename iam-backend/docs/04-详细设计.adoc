= 详细设计（功能分解 · F01–F28 + 真实数据版补充）
:toc:
:toclevels: 3


[NOTE]
====
版本：2026-10-26 · 与 `src/main/java/com/iam` 下的实现逐条对应
用法：一张卡 = 一个功能；卡片里的"验收用例"可以直接改成 Postman/Apifox 用例。
====


== 0. 阅读说明


* 每张卡固定 9 个字段：接口、权限、入参、校验、出参、Controller、Service、Mapper、异常、用例。
* 代码包：`auth` / `user` / `department` / `role` / `permission` / `apply` / `report`，公共能力在 `common`。
* 所有接口前缀 `/api`，除登录外都要 `Authorization: Bearer <sessionId>`。
* 统一返回：`{ code, data, message }`，`code = 0` 为成功。

== 1. 公共约定


=== 1.1 错误码


[cols="1,1,1",options="header"]
|===
|code |含义 |典型场景

|0 |成功 |—
|400 |参数或业务规则不满足 |工号格式错误、停用自己、删除自己、角色编码非法
|401 |未登录或会话失效 |无 token、token 过期、会话被撤销
|403 |已登录但无权限 |缺 `USER:VIEW`、账号已停用
|404 |资源不存在 |用户/角色 id 不存在
|409 |唯一键冲突或存在引用 |工号重复、角色编码重复、角色仍有成员
|500 |未预期异常 |SQL 执行失败等
|===


=== 1.2 鉴权


. `AuthInterceptor` 解析 `Authorization: Bearer <token>`；
. 查 `sys_session`：未撤销、未过期、用户启用，否则 401；
. 用 `PermissionMapper.codesOf(userId)` 取权限集合放进 `SessionContext`；
. 读方法上的 `@RequirePerm`，缺权限直接写 403，响应体带 `requiredPerm`。

=== 1.3 权限码


管理权限使用 `资源:动作`，跨系统业务权限使用 `系统:模块:功能:动作`。核心动作：
`VIEW / ADD / EDIT / DELETE / EXPORT / APPROVE / ASSIGN / ASSIGN_ROLE / ASSIGN_PERM`。

'''


== 2. 功能卡


=== F01 登录


[cols="1,1",options="header"]
|===
|项 |内容

|接口 |`POST /api/auth/login`
|权限 |匿名
|入参 |`account`（工号）、`password`
|校验 |两项非空；未处于锁定期；账号存在；BCrypt 匹配；`status = 1`
|出参 |`sessionId`、`expireAt`、`user`、`roles[]`、`permissions[]`、`menus[]`
|Controller |`AuthController.login`
|Service |`AuthService.login`：查锁定 → 校验密码 → UUID → 写会话 → 组装 profile
|Mapper |`UserMapper.findByAccount`、`SessionMapper.create`、`PermissionMapper.codesOf`
|异常 |400 空参数；401 账号或密码错误；403 账号停用；429 连续失败 5 次锁定 15 分钟
|用例 |① `SG900001/123456` → code 0、20 枚权限、7 个菜单；② 错密码 → 401 且提示剩余次数；③ 停用账号 → 403；④ 空密码 → 400；⑤ 连续 5 次错误 → 第 5 次返回 429，15 分钟内再登录仍 429
|===

=== F22 我的申请 / 待办列表


[cols="1,1",options="header"]

|异常 |401 / 403
|用例 |① 张伟的 mine 含自己提交的单；② 张伟（技术部主管）待办只含技术部李四的单；③ 王五（财务部）的单不出现在张伟待办；④ 系统管理员（ADMIN 角色）跳过部门限制，返回全系统待办

=== F23 审批


[cols="1,1",options="header"]
|===
|项 |内容

== 8. 真实数据版覆盖说明


本节优先级高于前文历史示例中的账号、数量和部门名称。

=== 8.1 数据基线


* `sys_department.parent_id` 为部门树自关联字段；
* 部门共 111 个：总公司、11 个总部部门、9 个分公司、90 个分公司部门/项目经理部；
* 代表员工 10 名，使用真实姓名、SG 工号和真实手机号；
* 前三系统共 42 个功能点，每点生成 VIEW/ADD/EDIT/DELETE/EXPORT/APPROVE 六类权限；
* IAM 管理权限 22 枚，权限总数 274 枚；
* 业务权限全部按 Excel 岗位列写入 `sys_role_permission`；`sys_user_permission` 种子行为 0。

=== 8.2 角色体系


[cols="1,1,1",options="header"]
|===
|角色 |职责 |授权原则

|SYS_ADMIN |用户、部门、权限目录维护 |USER:*、PERM:*、DEPT:*，无业务与 ROLE 权限
|SEC_ADMIN |角色维护、角色分配、权限审批 |ROLE:*、APPLY:APPROVE，无用户管理和业务权限
|AUDITOR |全局审计查看 |所有 VIEW，零写权限
|LEADER |公司领导业务 |Excel 公司领导列，52 枚
|MGR |部门经理业务 |Excel 部门经理列，67 枚
|PM |项目经理业务 |Excel 项目经理列，51 枚
|EMP |普通员工业务 |Excel 普通员工列，43 枚
|SUPER_ADMIN |超级管理员全权 |全部 274 项管理权限与业务权限
|===


SEC_ADMIN 同时拥有 `APPLY:APPROVE`，因此审批待办走全系统分支；普通 MGR 仍只查看和审批本人担任主管的部门。
