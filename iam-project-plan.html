IAM 第一次检查：原型 + API + 数据库 + 详细设计

10 天窗口（10/17–10/26）完成四步交付，10/27–10/29 接受检查。第一次检查要求「原型界面 + 完整后端」，但不做前后端联调。

周期 2026-10-17 ~ 2026-10-29 范围：RBAC0 6 张表 · 22 个接口 · 8 个页面 默认 4 人分工

01先把「完整」定义清楚

「完整后端」不等于「前端能调通」。本次的口径是：后端能独立启动、数据库能一键重建、22 个接口全部可用、鉴权真实生效，用接口工具演示，不改前端一行代码。

交付项完成的判定标准（DoD）谁来验
原型界面登录 → 我的权限 → 403 → 角色矩阵 → 分配角色 → 重登生效，全程无断点；8 个页面可进入全员彩排
数据库6 张表 DDL + 种子数据 + 重置脚本；一条命令重建；外键/唯一索引齐全数据负责人
接口22 个接口全部实现，返回 {code,data,message}；未登录 401、无权限 403、重复编码 409测试负责人
鉴权会话表 + 拦截器；菜单/路由/接口三层同源；停用用户、改角色立刻使会话失效后端 A
详细设计F01–F20 每个功能一张「功能卡」：接口、Controller、Service、Mapper、入参、出参、权限码、用例文档负责人
演示材料5 分钟脚本 + Postman 集合 + 一键启动说明 + 录屏兜底全体
明确不做：审批、差量、例外、项目域、组织树、审计报表、角色继承（RBAC1）、约束（RBAC2）。这些在 v0.5/v0.6 里都有文字说明，检查时只用一句话带过，不展开演示。

03四步的顺序与依赖

原型已经先行，所以后面三步不是串行，而是「接口定契约、数据库定结构、两边并行实现、最后用详细设计对齐」。

阶段输入输出完成标准
① 界面原型v0.6 范围、权限码规范8 个页面 + 路由守卫 + 403 + 演示脚本路径可点通（已完成）
② API 设计F01–F20 功能清单openapi.yaml：22 个接口、统一返回、错误码、鉴权头前端 mock 与后端实现都按它写
③ 数据库设计接口里的数据结构6 张表 DDL、索引、外键、种子与重置脚本一条命令重建，数据可复现
④ 详细设计②③ + 面向功能约束F01–F20 功能卡：Controller/Service/Mapper/入参/出参/权限码/用例每张卡能直接对着写代码

为什么接口在数据库之前

  • 接口描述“系统对外承诺什么”，表结构是它的实现细节
  • 先定接口，表结构只需支撑这些字段，避免建了用不上的表
  • 前端 mock 已经在按接口字段命名，反过来会改两次

但表结构要先于编码

  • 10/18 把 DDL 定稿，后端 10/19 才能直接写 Mapper
  • 之后只允许加字段、加索引，不允许改语义
  • 变更走 db/migration/V*.sql，不手改库

05详细设计怎么「分解」

v0.6 定的是面向功能实现：一个功能一条链，不做领域实体、继承、多态。所以分解的单位是「功能编号 F01–F20」，不是「实体」。

包结构（按功能域分，不按层分）

com.iam
├── common      Result / BizException / GlobalHandler / AuthInterceptor / SessionContext
├── auth        AuthController / AuthService / SessionMapper / dto/{LoginReq,MeResp}
├── user        UserController / UserService / UserMapper / dto/{UserReq,UserResp,RoleAssignReq}
├── role        RoleController / RoleService / RoleMapper / dto/{RoleReq,PermAssignReq}
├── permission  PermissionController / PermissionService / PermissionMapper
└── report      ReportController / ReportService / ReportMapper

每个功能一张「功能卡」

字段填写要求
功能编号 / 名称F05 新增用户
接口POST /api/users，权限码 USER:ADD
入参 / 校验字段、类型、必填、长度、唯一性；错误码
出参成功返回什么；空值怎么表示
Controller方法签名 + 注解（权限码）
Service业务规则：账号唯一、初始密码 123456、创建后无角色
Mapper / SQL表名、关键 SQL、影响行数
验收用例正常 + 至少两个异常（重复账号、缺字段）
写法建议：每个功能卡不超过一页，写完直接能照着敲代码。20 张卡 ≈ 20 页，正好是详细设计的体量；不要写成 60 页的“架构散文”。

06协作规则（防止并行打架）

  • 契约唯一真源：接口字段只认 openapi.yaml；谁要改字段，先改契约，再改两边代码，PR 里附一句“改契约”。
  • DDL 独占：只有数据负责人能改 schema.sql；其他人提变更单，不直接改库。
  • 公共类先合：10/19 上午先把 Result / BizException / AuthInterceptor 合进主干，两个人再分头写，否则各写一套返回结构。
  • 分支与合并：feat/auth、feat/user、feat/role、docs/design；每天 18:00 前合并一次，避免最后一天大合并。
  • 每日 15 分钟站会：昨天完成 / 今天计划 / 阻塞点；只同步这三件事。
  • 验收口径写在仓库里：docs/acceptance.md 列 6 条 DoD，谁都能对照检查。

08检查当天的三条演示线

  1. 界面线（3 分钟）：李四登录 → 只有“我的权限” → 输 #/users 出 403 → 管理员登录 → 角色矩阵勾“财务报表查看/导出” → 给李四追加角色 → 李四重登菜单多一项。
  2. 接口线（2 分钟）：Postman 依次调 登录 → /auth/me（看权限集合）→ 用李四的会话调 GET /api/users（403）→ 加角色后再调 /auth/me（权限变多）。
  3. 设计线（2 分钟）：6 张表 ER 图 → 三表关联那条 SQL → 一张功能卡（F05 新增用户）→ 22 个接口清单。
不要做的事：现场改代码、现场装环境、现场导数据、现场解释“这个本来要做但没做”。所有演示动作在 10/26 彩排时定死。
